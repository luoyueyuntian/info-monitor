# 核心用户流程与页面骨架

更新时间：2026-06-01

## 1. 文档目的

这份文档用于回答 4 个问题：

1. 第一版产品中，用户最核心的使用流程是什么
2. 每个流程要解决什么任务
3. MVP 需要哪些页面或等价视图
4. 每个页面的职责边界是什么

这份文档的目标不是画高保真界面，而是先把用户心智、页面职责和主流程走通。

## 2. 设计前提

当前页面和流程设计基于以下已确认前提：

- 第一阶段定位是信息工作台
- 第一阶段主场景是价格监控和投资信息跟踪
- 产品核心单元是主题
- 标准化按信息类型组织
- MVP 重点验证“持续采集与沉淀 + 少量高价值提醒”

因此，这套页面不应该像：

- 纯 BI 大屏
- 纯消息提醒工具
- 纯配置平台

而应该更像：

> 一个围绕主题运行的、桌面优先的个人信息工作台。

## 3. 核心用户任务

从当前主场景出发，MVP 最需要支持的用户任务可以收敛成 5 类：

1. 新建一个主题并开始监控
2. 每天快速巡检最近发生了什么
3. 深入查看某个主题的历史与当前状态
4. 打开某条重要事件，确认是否值得处理
5. 发现来源异常并修复或暂停

如果这 5 类任务走不顺，哪怕功能再多，第一版也很难真正用起来。

## 4. 核心用户流程

### 4.1 流程 A：新建主题

这是用户第一次把一个真实需求放进系统的流程。

#### 目标

- 把一个想持续关注的信息目标变成一个可运行的主题

#### 适用示例

- 新建 `Surface Pro 8 16G + 512G` 价格主题
- 新建 “季度 GDP / CPI 跟踪” 主题
- 新建 “黄金价格跟踪” 主题

#### 目标流程

1. 用户点击“新建主题”
2. 输入主题名称
3. 选择主题类型或主要信息类型
4. 填写主题描述或关注目标
5. 添加一个或多个来源
6. 选择提醒方式
7. 保存并开始运行

#### 流程设计原则

- 要让用户感觉自己是在“建立一个长期关注主题”
- 不是在“配置一个复杂抓取任务”
- 首次创建要足够轻，但不能模糊关键项

#### MVP 必须收集的信息

- 主题名称
- 主题类型或主信息类型
- 至少一个来源
- 基础提醒方式

#### MVP 可选补充

- 描述
- 标签
- 优先级
- 目标价或阈值

### 4.2 流程 B：每日巡检

这是最重要的日常使用流程。

#### 目标

- 在最短时间内知道最近有哪些值得关注的新变化

#### 目标流程

1. 用户打开首页 / 收件箱
2. 先浏览高优先级事件
3. 再浏览最近更新的主题
4. 对感兴趣的事件进入详情
5. 对感兴趣的主题进入主题页继续查看

#### 设计重点

- 首页首屏必须回答“今天有什么值得看”
- 不应该先让用户面对大量原始记录
- 不应该要求用户先进入复杂筛选页面

#### 成功标准

- 用户能在几分钟内完成一次巡检
- 用户不会被大量低价值更新淹没

### 4.3 流程 C：深入查看主题

这是从“看提醒”进入“做跟踪”的关键流程。

#### 目标

- 了解某个主题当前状态、最近变化和历史趋势

#### 目标流程

1. 用户从首页或主题列表进入某个主题
2. 查看主题当前概览
3. 查看最近事件
4. 查看历史记录或趋势
5. 必要时进入来源或事件详情

#### 设计重点

- 主题页必须让用户快速建立“这个主题最近发生了什么”的整体感
- 不能只是简单列出原始记录

### 4.4 流程 D：处理重要事件

这是产品“筛选价值”的体现。

#### 目标

- 快速确认一条事件是否真的重要，是否需要后续动作

#### 目标流程

1. 用户点击一条事件
2. 查看事件标题、时间、来源、摘要
3. 查看变化依据或原始证据
4. 判断是否值得进一步关注
5. 标记已读、忽略、收藏或继续跟踪

#### 设计重点

- 事件详情必须先给结论，再给证据
- 用户应该能快速跳回原始来源
- “利空 / 利好”“最近 30 天新低”这类信息要一眼可见

### 4.5 流程 E：处理来源异常

这是长期运行系统里不可避免的维护流程。

#### 目标

- 当某个来源失效时，用户能快速发现并处理

#### 目标流程

1. 用户在首页或来源状态页看到异常提示
2. 进入来源状态页
3. 查看最近失败时间和失败来源
4. 手动重试、暂停或后续修复

#### 设计重点

- 这不是主流程，但必须能被及时发现
- 否则主题会“默默失效”，损害信任感

## 5. 页面骨架总览

MVP 建议至少包含以下 6 个页面或等价视图：

1. 首页 / 收件箱
2. 主题列表页
3. 新建 / 编辑主题页
4. 主题详情页
5. 事件详情页
6. 来源状态页

## 6. 页面骨架定义

### 6.1 首页 / 收件箱

#### 页面职责

- 作为每日巡检的第一入口
- 展示最近最值得看的事件
- 提供系统整体运行感知

#### 首屏建议包含

- 今日或最近的重要事件列表
- 高优先级提醒区
- 最近更新的主题
- 来源异常提示

#### 推荐信息结构

1. 顶部概览区
2. 重要事件区
3. 最近更新主题区
4. 来源异常区

#### 这个页面不应承担的职责

- 不做复杂配置中心
- 不展示大量低价值原始记录
- 不做复杂统计报表首页

#### 为什么它最重要

- 用户每天最可能先打开的就是这里
- 如果首页不能快速产生价值，产品很难形成习惯

### 6.2 主题列表页

#### 页面职责

- 统一管理所有主题
- 展示每个主题当前状态
- 支持快速进入某个主题

#### 每个主题卡片或行建议展示

- 主题名称
- 主题类型
- 当前状态
- 最近一次更新时间
- 最近一次重要事件时间
- 来源数量

#### 推荐操作

- 搜索主题
- 按类型筛选
- 按状态筛选
- 创建新主题

#### 这个页面不应承担的职责

- 不替代主题详情页
- 不展示完整历史和完整事件流

### 6.3 新建 / 编辑主题页

#### 页面职责

- 创建新主题
- 调整主题基础信息
- 管理主题绑定的来源与提醒

#### 推荐信息区块

1. 基础信息
2. 主题类型或信息类型
3. 来源列表
4. 提醒设置

#### MVP 设计建议

- 优先做成分段式表单
- 不必一开始追求复杂向导

#### 这个页面不应承担的职责

- 不做来源调试页
- 不做复杂规则可视化平台

### 6.4 主题详情页

#### 页面职责

- 呈现一个主题的全局视图
- 聚合这个主题的来源、记录、变化和事件
- 支持历史回看

#### 页面建议结构

1. 主题头部概览
2. 关键事件区
3. 最新记录区
4. 历史变化区
5. 来源列表区

#### 头部概览建议展示

- 主题名称
- 主题类型
- 当前状态
- 最近更新时间
- 关键指标或当前摘要

#### 关键事件区建议展示

- 最近 3 到 5 条重要事件
- 每条事件的时间、标签和简要结论

#### 历史变化区建议展示

- 时间线
- 或按日 / 周聚合的历史列表

#### 为什么主题页很关键

- 它决定产品是“提醒器”还是“工作台”
- 如果主题页足够好用，用户才会愿意长期沉淀信息资产

### 6.5 事件详情页

#### 页面职责

- 呈现单条高价值事件的完整上下文
- 帮助用户快速确认事件是否值得处理

#### 页面建议结构

1. 事件主结论
2. 事件元信息
3. 变化依据
4. 原始证据
5. 关联主题入口

#### 首屏建议展示

- 事件标题
- 事件标签
- 事件时间
- 主题名称
- 一句话结论

#### 变化依据区建议展示

- 价格前后变化
- 当前值 / 上期值 / 预期值
- 利空 / 利好判断依据

#### 原始证据区建议展示

- 来源名称
- 原始标题或原始摘要
- 原始链接

#### 推荐操作

- 标记已读
- 收藏
- 忽略
- 进入主题详情

### 6.6 来源状态页

#### 页面职责

- 统一查看来源健康状况
- 发现和管理失败来源

#### 建议展示

- 来源名称
- 所属主题
- 当前状态
- 最近成功时间
- 最近失败时间
- 简要错误提示

#### 推荐操作

- 手动刷新
- 暂停来源
- 返回主题

#### 这个页面为什么必须有

- 因为这是长期运行系统
- 没有来源健康页，用户很难知道“没消息”到底是没变化，还是来源坏了

## 7. 页面之间的关系

这几个页面应该形成清晰的跳转链路：

- 首页 -> 事件详情页
- 首页 -> 主题详情页
- 主题列表页 -> 主题详情页
- 主题详情页 -> 事件详情页
- 首页 / 主题页 -> 来源状态页
- 主题页 -> 编辑主题页

设计目标是：

- 用户从提醒进入主题很顺
- 用户从主题进入证据很顺
- 用户发现运行问题后能快速找到来源状态

## 8. MVP 页面优先级

### 8.1 P0 页面

- 首页 / 收件箱
- 主题列表页
- 主题详情页
- 事件详情页

这些页面直接决定产品是否可日常使用。

### 8.2 P1 页面

- 新建 / 编辑主题页
- 来源状态页

这些页面对系统长期运行同样重要，但在首轮展示价值时优先级略低于前四个核心视图。

## 9. 每个页面的最小可用标准

### 9.1 首页 / 收件箱

最少要做到：

- 能看到最新重要事件
- 能区分普通更新和重要事件
- 能进入事件详情和主题详情

### 9.2 主题列表页

最少要做到：

- 能看到所有主题
- 能知道主题是否正常运行
- 能进入主题详情

### 9.3 主题详情页

最少要做到：

- 能看见主题基础信息
- 能看见最近事件
- 能看见一段历史记录

### 9.4 事件详情页

最少要做到：

- 能看见事件结论
- 能看见事件依据
- 能跳到原始来源

### 9.5 来源状态页

最少要做到：

- 能看见失败来源
- 能看见最近运行状态

## 10. 当前版本的结论

当前可以明确：

- 第一版最重要的日常流程是“创建主题 -> 每日巡检 -> 进入主题 -> 查看事件 -> 处理来源异常”
- MVP 页面骨架应围绕首页、主题、事件、来源状态这几类视图展开
- 首页解决“今天看什么”，主题页解决“这个主题最近怎么样”，事件页解决“这件事值不值得处理”
