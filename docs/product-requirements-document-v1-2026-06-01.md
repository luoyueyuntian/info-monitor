## 2. 产品定义

### 2.1 一句话定义

这是一个围绕“主题”持续运行的个人信息工作台，用于从多个渠道收集和标准化信息，沉淀历史记录，识别关键变化，并通过提醒和回看帮助用户降低信息巡检成本。

### 2.2 当前阶段定位

当前阶段，这个产品优先是：

> 一个面向个人自用的、以价格监控和投资信息跟踪为核心场景的信息工作台。

它当前不是：

- 面向大众的通用 SaaS
- 全自动决策助手
- 通用 BI 平台
- 纯爬虫工具箱

### 2.3 当前阶段核心价值

第一阶段的核心价值有 4 个：

1. 围绕主题持续收集多渠道信息
2. 把同类信息标准化沉淀下来
3. 从变化中筛出少量高价值信号
4. 支持历史回看与低成本巡检

## 3. 背景与问题

### 3.1 当前信息处理方式的问题

你当前关心的信息分布在多个来源中：

- 二手平台、电商平台
- 指数、股票、黄金等价格渠道
- 统计局、人民银行等官方发布渠道
- 新闻、公告和其他公开发布渠道

当前主要问题是：

- 来源分散，需要手动重复查看
- 真正重要的变化混在大量普通更新里
- 历史信息不容易统一保存和回看
- 跨渠道对比困难
- 信息抓到了，但不容易形成稳定使用习惯

### 3.2 当前阶段要解决的核心问题

当前产品不以“替你做复杂决策”为第一目标，而是优先解决以下问题：

1. 如何围绕一个主题持续接入多个来源
2. 如何把同类信息跨来源标准化
3. 如何保存历史并识别有价值变化
4. 如何在不制造太多噪音的前提下提醒用户

## 4. 目标用户

### 4.1 当前核心用户

当前核心用户只有一个：你自己。

但为了后续抽象与复用，产品按 3 类角色理解当前需求。

### 4.2 角色优先级

当前阶段角色优先级如下：

1. 消费者
2. 个人投资者
3. 独立开发者

### 4.3 角色定义

#### 消费者

核心诉求：

- 监控目标商品价格
- 发现跨平台同配置低价
- 减少手动刷页面的频率

#### 个人投资者

核心诉求：

- 跟踪自己关心的价格、指数、政策和宏观数据
- 识别利空 / 利好事件
- 建立可回看的主题历史

#### 独立开发者

核心诉求：

- 持续跟踪产品更新、活动和后续扩展场景

说明：

- 这一角色当前保留为后续扩展方向，不是第一阶段主服务对象

## 5. 产品目标

### 5.1 第一阶段目标

第一阶段要做的不是“覆盖尽可能多场景”，而是建立一套你会长期使用的工作流。

具体目标：

1. 让主题成为统一的长期关注入口
2. 让多来源信息持续被采集和沉淀
3. 让价格类和投资类高价值信号可被发现
4. 让用户可以通过首页、主题页和事件页完成日常巡检

### 5.2 MVP 要验证的核心假设

1. 主题作为入口是顺手的
2. 多渠道标准化沉淀是有长期价值的
3. 最近 30 天新低和利空 / 利好事件是有用的提醒
4. 这个系统能替代一部分手工巡检

### 5.3 当前不追求的目标

当前不追求：

- 多用户协作
- 面向陌生用户的通用配置体验
- 复杂无代码能力
- 自动交易或自动执行
- 完整趋势 / 舆情平台能力

## 6. 产品原则

### 6.1 主题优先

产品优先围绕“主题”组织，而不是围绕脚本、来源或规则组织。

### 6.2 类型优先

标准化优先按信息类型组织，而不是按站点组织。

### 6.3 历史优先

产品不仅要保存当前信息，还要支持历史回看和变化识别。

### 6.4 少而准的提醒优先

提醒价值比提醒数量更重要。

### 6.5 证据可追溯

所有重要事件和结论都应能追溯回原始来源。

### 6.6 先自用闭环，再平台化扩展

第一阶段优先保证你自己愿意持续使用，而不是一开始就平台化过度。

## 7. 核心对象

本产品当前采用以下核心对象体系：

1. 主题
2. 来源
3. 原始记录
4. 标准化记录
5. 变化
6. 事件
7. 洞察
8. 摘要

主链路为：

`主题 -> 来源 -> 原始记录 -> 标准化记录 -> 变化 -> 事件 -> 洞察 / 摘要`

### 7.1 主题

主题是一项需要被持续收集、标准化、观察和回看的信息关注单元。

### 7.2 来源

来源是某个主题的信息采集入口。

### 7.3 标准化记录

标准化记录是按信息类型整理后的统一结果，用于后续历史、比较、提醒和分析。

### 7.4 事件

事件是变化中值得被用户看到、提醒或进一步处理的部分。

## 8. 第一版支持的信息类型

第一版支持 4 类信息类型：

1. 价格类
2. 内容更新类
3. 新闻 / 公告类
4. 金融指标 / 事件类

其中第一阶段主类型是：

- 价格类
- 金融指标 / 事件类

第一阶段支撑类型是：

- 新闻 / 公告类
- 内容更新类

## 9. 场景范围

### 9.1 第一阶段主场景

#### 场景 A：价格监控

要支持：

- 围绕一个价格主题配置多个来源
- 跨平台同配置价格记录标准化
- 历史价格回看
- 最近 30 天新低提醒

#### 场景 B：投资信息跟踪

要支持：

- 围绕一个投资主题配置多个来源
- 价格、新闻 / 公告、金融指标 / 事件信息的主题化沉淀
- 利空 / 利好事件识别
- 历史回看与重点提醒

### 9.2 第一阶段支撑场景

#### 新闻 / 公告跟踪

定位：

- 作为投资信息跟踪的重要事实来源层

#### 内容更新跟踪

定位：

- 先纳入标准化体系
- 为后续扩展场景打基础

### 9.3 暂缓场景

第一阶段暂不重点展开：

- UGC 热度快速上升
- 复杂趋势分析
- 复杂舆情与情绪分析

## 10. 高价值信号定义

当前已明确的高价值信号如下：

### 10.1 价格类

- 最近 30 天新低

当前已确认的价格比较口径：

- 跨平台
- 同配置

当前后续仍需细化：

- 二手商品成色差异
- 地区差异
- 缺少完整配置字段时的归类

### 10.2 金融指标 / 事件类

- 利空事件
- 利好事件

当前后续仍需细化：

- 哪些事件可以明确判为利空
- 哪些事件可以明确判为利好
- 哪些事件应保持中性，仅做记录

## 11. 功能需求

### 11.1 主题管理

系统必须支持：

- 创建主题
- 编辑主题
- 暂停主题
- 恢复主题
- 查看主题列表

### 11.2 来源管理

系统必须支持：

- 为主题添加多个来源
- 查看来源状态
- 手动触发来源刷新
- 暂停来源

### 11.3 标准化沉淀

系统必须支持：

- 价格类记录标准化
- 金融指标 / 事件类记录标准化
- 新闻 / 公告类基础标准化
- 基础历史记录保存

### 11.4 历史回看

系统必须支持：

- 查看某主题的历史记录
- 按时间查看变化
- 回看关键事件

### 11.5 事件识别

系统必须支持：

- 最近 30 天新低识别
- 利空 / 利好事件识别

### 11.6 提醒与摘要

系统必须支持：

- 即时提醒
- 按主题查看重要事件
- 基础摘要视图

### 11.7 运行状态可见

系统必须支持：

- 查看主题运行状态
- 查看来源最近成功时间
- 查看来源最近失败情况

## 12. 核心用户流程

### 12.1 新建主题

目标流程：

1. 输入主题名称
2. 选择主题类型或主信息类型
3. 添加一个或多个来源
4. 配置基础提醒方式
5. 保存并开始运行

### 12.2 每日巡检

目标流程：

1. 打开首页 / 收件箱
2. 浏览最近重要事件
3. 查看最近更新主题
4. 进入事件详情或主题详情

### 12.3 深入查看主题

目标流程：

1. 从首页或主题列表进入主题
2. 查看主题概览
3. 查看最近事件
4. 查看历史记录与变化

### 12.4 处理重要事件

目标流程：

1. 打开事件详情
2. 查看结论
3. 查看变化依据和原始来源
4. 判断是否继续关注

### 12.5 处理来源异常

目标流程：

1. 发现来源异常提示
2. 打开来源状态页
3. 查看异常来源与最近失败时间
4. 手动刷新、暂停或后续修复

## 13. 页面需求

MVP 建议至少包含以下 6 个页面或等价视图：

1. 首页 / 收件箱
2. 主题列表页
3. 新建 / 编辑主题页
4. 主题详情页
5. 事件详情页
6. 来源状态页

### 13.1 首页 / 收件箱

职责：

- 展示最近值得关注的事件
- 作为每日巡检第一入口
- 显示来源异常提示

### 13.2 主题列表页

职责：

- 展示所有主题
- 展示主题状态和最近更新时间

### 13.3 新建 / 编辑主题页

职责：

- 创建新主题
- 编辑主题信息
- 管理来源和提醒方式

### 13.4 主题详情页

职责：

- 聚合展示主题概览、历史记录、关键事件和来源

### 13.5 事件详情页

职责：

- 展示单条事件的结论、依据和原始来源

### 13.6 来源状态页

职责：

- 统一查看来源健康情况和异常状态

## 14. MVP 范围

### 14.1 MVP 必须具备

- 主题管理
- 多来源接入与管理
- 价格类标准化
- 金融指标 / 事件类标准化
- 新闻 / 公告类基础标准化
- 历史记录保存与回看
- 最近 30 天新低识别
- 利空 / 利好事件识别
- 首页巡检视图
- 主题详情视图
- 事件详情视图
- 来源状态可见

### 14.2 MVP 推荐具备但可简化

- 新闻 / 公告类基础摘要
- 内容更新类基础接入
- 基础筛选能力

### 14.3 MVP 明确不做

- 多用户协作
- 权限体系
- 完整无代码配置
- 通用规则 DSL
- 复杂工作流编排
- 复杂趋势 / 热度分析
- 自动交易或自动执行
- 完整移动端产品

## 15. 成功标准

### 15.1 使用结果

- 你愿意持续维护若干真实主题
- 你愿意每天或每周打开系统查看
- 你减少了手工巡检频率

### 15.2 信息质量结果

- 历史价格能稳定积累
- 金融事件能持续记录
- 最近 30 天新低和利空 / 利好提醒有实际价值

### 15.3 产品体验结果

- 主题心智清晰
- 首页可完成快速巡检
- 主题页和事件页可支撑回看与确认
- 来源异常可被及时发现

## 16. 风险与后续细化项

### 16.1 价格类口径细化

仍需后续明确：

- 二手商品成色
- 地区差异
- 配置缺失时的归类策略

### 16.2 利空 / 利好事件细化

仍需后续明确：

- 不同事件类型的方向性判断规则
- 中性事件的处理方式

### 16.3 内容更新类深度

当前进入第一版体系，但暂不作为主交付重点，后续可根据真实使用反馈决定是否提升优先级。

## 17. 当前结论

这份 PRD v1 明确了当前第一阶段的产品基线：

- 产品定位是个人信息工作台
- 核心单元是主题
- 主场景是价格监控和投资信息跟踪
- 标准化按信息类型组织
- 第一版重点验证多来源沉淀、历史回看与高价值提醒链路

这意味着后续已经可以基于这份 PRD 进入：

- 技术方案设计
- 开发任务拆解
- 首版页面与交互细化
