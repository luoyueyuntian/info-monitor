# 系统架构与技术方案 v1

更新时间：2026-06-01

## 1. 文档目的

这份文档用于把当前产品结论翻译成一版可落地的技术方案，回答 6 个问题：

1. 第一版系统应该怎么分层
2. 哪些模块必须存在
3. 数据应该如何流动
4. 技术栈应该如何选择
5. 哪些地方应该先做简单，哪些地方要提前留扩展位
6. 第一轮开发应该按什么顺序推进

这份文档基于 [PRD v1](/Users/xhh/work/explord/info-monitor/docs/product-requirements-document-v1-2026-06-01.md) 和此前几份产品文档，不再重新讨论产品目标本身。

## 2. 输入约束

当前技术方案必须满足以下产品和现实约束：

- 第一阶段优先做信息工作台，不做复杂平台化
- 第一阶段主场景是价格监控和投资信息跟踪
- 核心单元是主题
- 标准化按信息类型组织
- 第一版重点能力是多来源采集、标准化、历史回看和高价值提醒
- 前后端从一开始就要分离
- 前端使用 Vue 3
- 爬虫和数据处理使用 Python
- 其他后端服务使用 Node.js
- 你能接受新增适配代码，但不希望每加一个来源就重构系统

## 3. 技术目标

### 3.1 第一版技术目标

第一版技术方案最重要的目标不是“高并发”和“高扩展”，而是：

1. 能稳定接入多个来源
2. 能把原始数据和标准化数据保存下来
3. 能围绕主题持续运行
4. 能识别变化并生成事件
5. 能支撑一个前后端分离、可日常使用的桌面优先工作台

### 3.2 第一版不优先追求的技术目标

当前不优先追求：

- 大规模分布式采集
- 多租户架构
- 复杂微服务拆分
- 通用规则平台
- 全量实时流式架构
- 复杂跨语言 RPC 体系

## 4. 推荐总体架构

### 4.1 一句话方案

第一版推荐采用：

> 前后端分离的多语言单仓库架构：`Vue 3 前端` + `Node.js 业务后端` + `Python 抓取与数据处理子系统`，通过共享 PostgreSQL 和清晰的内部边界协作。

### 4.2 为什么这样拆

因为当前阶段最重要的是：

- 满足前后端分离的技术偏好
- 让前端可以独立演进
- 让抓取与数据处理能力沉淀在 Python 子系统
- 让主题管理、页面聚合、通知等通用服务集中在 Node.js
- 同时避免一开始拆成很多重服务

如果一开始再继续细拆，会明显增加：

- 开发成本
- 调试成本
- 运维复杂度
- 跨语言同步成本

### 4.3 运行角色

推荐把系统拆成 4 个主要运行角色：

1. `Frontend`
2. `Node API`
3. `Python Scheduler`
4. `Python Worker`

其中：

- Frontend 和 Node API 通过 HTTP/JSON 通信
- Node API 和 Python 子系统通过共享数据库协作
- 所有运行角色共享 PostgreSQL 作为核心状态存储

#### Frontend

负责：

- 提供用户界面
- 展示主题、事件、历史、来源状态
- 发起主题管理、筛选、手动刷新等操作

#### Node API

负责：

- 提供主题、来源、事件、历史相关 REST API
- 聚合首页、主题页、事件页所需数据
- 接收手动触发请求
- 管理提醒配置
- 承担通知下发等业务服务

#### Python Scheduler

负责：

- 扫描到达运行时间的来源
- 生成采集任务
- 控制频率、重试、暂停状态

#### Python Worker

负责：

- 执行来源采集
- 保存原始记录
- 做标准化
- 做变化检测
- 生成事件和摘要输入
- 回写运行结果和状态

## 5. 推荐技术栈

### 5.1 前端

推荐：

- `Vue 3`
- `TypeScript`
- `Vite`
- `Vue Router`
- `Pinia`

推荐理由：

- Vue 3 适合长期演进
- TypeScript 有利于维护页面状态和接口契约
- Vite 启动和迭代成本低
- Router 和 Pinia 足够支撑工作台型产品

说明：

- UI 组件库可以后续选择，例如 `Naive UI` 或 `Element Plus`
- 第一版更重要的是把页面职责和数据链路跑通，不需要一开始追求很重的前端基建

### 5.2 Node.js 业务后端

推荐：

- `Node.js`
- `TypeScript`
- `Fastify`

推荐理由：

- 足够轻，适合当前阶段
- TypeScript 对接口、DTO 和业务模块更友好
- 比一开始就上更重的服务框架更适合独立开发快速迭代

说明：

- 如果后续业务层明显复杂化，可以再演进
- 当前阶段更应该保持后端 API 层轻量

### 5.3 Python 抓取与数据处理

推荐：

- `Python 3.11+`
- `httpx`
- `feedparser`
- `BeautifulSoup` 或 `selectolax`
- `Playwright`

推荐策略：

- 能不用浏览器就不用浏览器
- 能用 API/RSS 就优先 API/RSS
- 浏览器采集只留给动态站点和必要场景

### 5.4 数据库

推荐：

- `PostgreSQL`

推荐理由：

- Node 和 Python 都可以稳定接入
- 关系结构适合主题、来源、记录、变化、事件等核心实体
- 支持 JSON 字段，适合部分半结构化内容
- 适合做历史记录、对比和查询

### 5.5 数据访问与迁移策略

由于 Node 和 Python 都要访问同一套数据库，第一版推荐：

- Node 侧使用 `Kysely` 或类似轻量 Query Builder
- Python 侧使用 `SQLAlchemy Core/ORM`
- 数据库迁移采用 `SQL-first` 策略

推荐理由：

- 避免 Node ORM 与 Python ORM 各自维护完整 schema，导致漂移
- 让数据库结构成为跨语言共享边界
- 对独立开发者来说更容易理解和调试

说明：

- 当前不推荐 Node 和 Python 各自维护独立迁移体系
- 也不推荐把某一侧 ORM 直接当成唯一 schema 真相

### 5.6 定时与任务执行

第一版推荐：

- Python 侧使用 `APScheduler` 或系统级 `cron` 负责调度
- 数据库中的任务表负责排队和状态管理
- Python Worker 轮询或消费待执行任务

推荐理由：

- 对 Python 子系统足够轻
- 不需要一开始就上跨语言消息中间件
- 足够支撑第一版主题级定时采集与运行管理

后续升级方向：

- 如果任务量、并发和跨语言协作复杂度明显提升，再引入 Redis Streams、RabbitMQ 或其他更强队列系统

### 5.7 数据处理与分析

推荐：

- `Pydantic`：定义标准化记录结构
- `pandas`：做时间序列和对比分析
- 规则判断逻辑直接写在 Python 代码中

说明：

- 第一版不要引入复杂规则 DSL
- 规则逻辑先代码化，和真实样本一起迭代

### 5.8 原始快照存储

推荐：

- 开发环境：本地文件系统
- 生产环境：对象存储或兼容 S3 的存储

推荐理由：

- 原始 HTML / JSON / 文本记录不适合全部塞进数据库主表
- 需要为排错和追溯保留原始证据

### 5.9 通知

推荐做一个统一通知抽象层，第一版先支持 1 到 2 个通道即可。

可选：

- 邮件
- Webhook
- Telegram
- 飞书 / 企业微信机器人

建议：

- 第一版优先选你自己最常用、最稳定的通道
- 通知下发统一放在 Node 侧处理

### 6.1 `apps/frontend`

负责：

- Vue 3 页面
- 路由
- 状态管理

### 6.2 `apps/api`

负责：

- Node.js 业务 API
- 主题、来源、事件等资源接口
- 首页与主题页聚合查询
- 手动触发与通知配置

### 6.3 `apps/python-worker`

负责：

- 来源适配器
- 抓取执行
- 标准化
- 变化检测
- 事件生成

### 6.4 `apps/python-scheduler`

负责：

- 扫描待运行来源
- 创建运行任务
- 控制重试和暂停状态

### 6.5 `packages/shared-contracts`

负责：

负责共享数据库迁移脚本。

- `storage/`
- `analysis/`

## 7. 核心处理链路

### 7.1 主链路

系统核心链路建议固定为：

`主题 -> 来源 -> 采集运行 -> 原始记录 -> 标准化记录 -> 变化检测 -> 事件判断 -> 通知 / 摘要 / 页面展示`

### 7.2 运行时数据流

一次来源运行的建议流程：

1. Node API 创建主题、来源和提醒配置
2. Python Scheduler 扫描到达运行时间的来源或手动触发请求
3. Python Scheduler 创建运行任务
4. Python Worker 领取任务
5. 调用来源适配器抓取数据
6. 保存原始记录和运行元信息
7. 调用对应信息类型标准化器生成标准化记录
8. 与历史记录比较，生成变化
9. 根据规则判断是否形成事件
10. 将事件写回数据库
11. Node API 或 Node 后台任务读取新事件并发送通知
12. 前端通过 Node API 读取主题、事件、历史和状态数据

### 7.3 为什么这条链要固定

因为这条链正是你要沉淀的核心能力：

- 采集
- 沉淀
- 对比
- 判断
- 输出

后面扩场景时，尽量复用这条链，而不是为每个场景重写流程。

## 8. 适配器架构建议

### 8.1 不追求通用爬虫，追求统一适配器协议

第一版不要试图做一个包打天下的抓取引擎。

更合理的做法是：

- 每个来源有自己的适配实现
- 所有适配实现遵循统一输入输出协议

### 8.2 推荐适配器协议

每个适配器至少负责两件事：

1. `fetch`
2. `map_to_normalizer_input`

更具体地说：

- `fetch`：从来源拿到原始内容
- `map_to_normalizer_input`：把来源原始结构映射成标准化器可处理输入

如果需要更清晰，也可以拆成：

- `fetch`
- `parse`
- `normalize`

### 8.3 适配器输入

建议适配器输入至少包含：

- 主题信息
- 来源配置
- 上次运行上下文
- 当前运行上下文

### 8.4 适配器输出

建议统一输出：

- 原始内容
- 运行元信息
- 标准化记录列表

### 8.5 适配器分级

第一版建议按复杂度分 4 类：

1. API 适配器
2. RSS 适配器
3. 静态页面适配器
4. 动态页面适配器

优先级建议：

- 优先做 API / RSS
- 再做静态页面
- 最后才做 Playwright 类动态页面

## 9. 标准化层设计

### 9.1 标准化器按信息类型组织

标准化器不应按来源组织，而应按信息类型组织：

- 价格类标准化器
- 内容更新类标准化器
- 新闻 / 公告类标准化器
- 金融指标 / 事件类标准化器

### 9.2 标准化层职责

标准化层负责：

- 字段映射
- 字段清洗
- 类型转换
- 时间规范化
- 结构补齐
- 去掉明显噪音字段

### 9.3 标准化层不负责什么

第一版不建议让标准化层直接承担：

- 复杂事件判断
- 跨主题聚合
- 复杂模型推理

这些更适合放在后面的变化检测和分析层。

## 10. 变化检测与事件判断

### 10.1 为什么分两层

第一版建议明确区分：

- 变化检测
- 事件判断

原因：

- 变化是客观差异
- 事件是值得提醒的变化

不分层的话，后面很容易把比较逻辑和提醒逻辑混在一起。

### 10.2 变化检测层

职责：

- 识别新增记录
- 识别字段变化
- 识别价格变化
- 识别同主题内新出现的数据点

### 10.3 事件判断层

职责：

- 判断是否创最近 30 天新低
- 判断是否为利空事件
- 判断是否为利好事件
- 决定是否需要提醒

### 10.4 第一版规则建议代码化

第一版建议直接在 Python 代码中实现这些判断逻辑，不做可视化规则引擎。

理由：

- 规则数量不多
- 场景还在探索期
- 代码化更容易和真实样本一起迭代

## 11. 存储设计建议

### 11.1 主数据库中应存什么

PostgreSQL 中建议保存：

- 主题
- 来源
- 运行任务
- 原始记录索引
- 标准化记录
- 变化
- 事件
- 通知记录

### 11.2 数据归属建议

为了降低 Node 与 Python 的边界混乱，建议按职责划分数据归属：

- Node 主导：主题、来源配置、提醒配置、通知记录、前端查询视图
- Python 主导：运行任务、原始记录、标准化记录、变化、事件生成结果
- 双方共享读取：主题、来源、事件、运行状态

### 11.3 文件或对象存储中应存什么

建议保存：

- HTML 快照
- 原始 JSON
- 长文本原文
- 调试用截图或附件

### 11.4 为什么不要把一切都塞数据库

因为：

- 原始内容体积可能大
- 后续排错和对比时更适合文件式保存
- 主库更适合保存结构化索引和业务状态

## 12. 数据模型建议

这一部分是架构级建议，不展开到完整字段级表设计。

### 12.1 核心实体

建议至少有以下核心实体：

- `themes`
- `sources`
- `source_runs`
- `raw_snapshots`
- `normalized_records`
- `changes`
- `events`
- `notifications`

可按职责再分：

- Node 侧主要使用：`themes`、`sources`、`notifications`
- Python 侧主要使用：`source_runs`、`raw_snapshots`、`normalized_records`、`changes`、`events`

### 12.2 关键关系

- 一个主题有多个来源
- 一个来源有多次运行
- 一次运行产生一个或多个原始记录
- 原始记录生成一个或多个标准化记录
- 标准化记录与历史比较后产生变化
- 一部分变化会变成事件

## 13. 页面与接口层建议

### 13.1 前端页面层

第一版页面层应优先实现：

- 首页 / 收件箱
- 主题列表
- 新建 / 编辑主题
- 主题详情
- 事件详情
- 来源状态页

### 13.2 Node API 策略

由于从一开始就是前后端分离，Node API 应明确提供以下边界：

- 主题相关接口
- 来源相关接口
- 事件相关接口
- 历史记录接口
- 手动触发接口
- 运行状态接口

理由：

- 方便前端独立开发
- 方便 Node 侧形成稳定 BFF / 业务 API 层
- 方便后续自动生成前端类型或 SDK

### 13.3 推荐契约方式

建议：

- Node API 维护 OpenAPI 文档
- 前端基于 OpenAPI 生成或校验接口类型
- Python 与 Node 的内部协作优先通过数据库边界，而不是一开始就做复杂内部 RPC

### 13.4 为什么内部协作先不做 RPC

因为当前阶段：

- 共享数据库已经足够支撑 MVP
- 如果一开始引入 gRPC 或跨语言消息总线，复杂度会上升
- 对你当前最重要的抓取与数据沉淀主链没有本质帮助

## 14. 通知设计建议

### 14.1 通知不应该直接散落在各模块里

建议统一由 Node 侧通知服务负责：

- 接收事件
- 根据主题配置判断是否发送
- 选择通知通道
- 记录通知结果

### 14.2 第一版通知粒度

建议至少支持两种粒度：

- 即时事件通知
- 每日或定时摘要通知

### 14.3 通知去重

第一版建议考虑最基本的去重能力：

- 同一事件不重复轰炸
- 同一运行中的重复变化不重复发送

## 15. 运行可观测性

### 15.1 第一版必须有的运行可见性

建议至少记录并可展示：

- 来源最近成功时间
- 来源最近失败时间
- 失败原因摘要
- 最近一次运行耗时
- 当前是否暂停

### 15.2 为什么这部分必须尽早做

因为信息监控系统最怕的不是“偶尔失败”，而是“默默失效”。

没有运行可见性，你很难判断：

- 真的是没有新信息
- 还是来源坏了
- 还是标准化逻辑出问题了

## 16. LLM 与分析能力建议

### 16.1 第一版不要让 LLM 站在主链路最前面

第一版主链路应优先依赖：

- 结构化抓取
- 标准化
- 规则判断

而不是先依赖模型去“理解一切”。

### 16.2 第一版 LLM 的合适位置

LLM 更适合放在：

- 新闻 / 公告简摘要
- 事件一句话总结
- 后续每日摘要生成

### 16.3 为什么要这样放

因为当前阶段你最想沉淀的是数据能力，而不是把系统建立在不稳定推理上。

## 17. 安全与合规提醒

### 17.1 第一版应保留来源策略意识

即使当前是自用，也建议在来源层面保留以下信息：

- 来源类型
- 是否有官方 API
- 是否需要登录
- 是否存在明显使用限制

### 17.2 建议优先使用更稳定、更合规的数据入口

优先级建议：

1. 官方 API
2. RSS / Feed

## 18. 第一轮开发顺序建议

### 18.1 第 1 步：打通最小主链路

先完成：

- Vue 3 前端基础工程
- Node API 基础工程
- Python Worker / Scheduler 基础工程
- 主题与来源的最小 CRUD
- 一种简单来源适配器
- 原始记录保存
- 一种标准化器
- 首页和主题页最小视图

目标：

- 系统从 0 到 1 跑通一次

### 18.2 第 2 步：先做价格类闭环

建议优先做：

- 二手价格主题
- 跨平台同配置价格标准化
- 最近 30 天新低判断
- 价格事件提醒

理由：

- 样本清楚
- 价值直接
- 能快速验证主链路

### 18.3 第 3 步：补投资信息主链

建议再接入：

- 宽基指数每日结果
- 统计局公开数据
- 人民银行公开数据
- 利空 / 利好事件逻辑

### 18.4 第 4 步：补运行可见性与通知

建议把：

- 来源状态页
- 失败记录
- 基础通知

尽早补齐，否则系统很快会变得难维护。

## 19. 未来升级路径

如果第一版跑通，后续自然升级方向包括：

- 更强的价格异常识别
- 更细的利空 / 利好规则
- 新闻 / 公告更强摘要
- 内容更新类深化
- 趋势 / 热度类纳入
- 更强的前端交互
- 更成熟的任务队列和跨语言协作方式

## 20. 当前版本结论

当前最合适的技术路线是：

- 前端：Vue 3 + TypeScript + Vite
- 业务后端：Node.js + TypeScript + Fastify
- 抓取与数据处理：Python
- 数据库：PostgreSQL
- 调度与执行：Python Scheduler + Worker
- 协作边界：共享数据库优先，RPC/消息总线后置
- 标准化按信息类型组织
- 规则优先，LLM 作为增强

这条路线既满足你从一开始前后端分离的要求，也保留了 Python 子系统作为抓取与数据处理核心的独立性，整体上更符合你当前的开发偏好和能力积累目标。
