# 场景地图与阶段优先级

更新时间：2026-06-01

## 1. 文档目的

这份文档用于回答 4 个问题：

1. 当前产品涉及哪些主要场景
2. 哪些场景属于第一阶段主场景
3. 哪些场景作为支撑或后续扩展保留
4. 场景优先级为什么这样排

这份文档的目标，是在正式写 MVP 和 PRD 前，把“先做什么、不先做什么”切清楚。

## 2. 场景划分原则

当前场景划分遵循 4 个原则：

1. 优先服务已确认的角色优先级
2. 优先服务高频、刚需、自用价值明确的场景
3. 优先服务已经有真实样本的场景
4. 优先服务能沉淀抓取与标准化通用能力的场景

基于当前前置决策，第一阶段的角色优先级为：

1. 消费者
2. 个人投资者
3. 独立开发者

因此，场景优先级也应围绕这个顺序展开。

## 3. 场景总览

当前产品可以识别出的场景，按类型可分为 5 组：

1. 价格监控
2. 投资信息跟踪
3. 内容更新跟踪
4. 新闻 / 公告跟踪
5. 趋势 / 热度跟踪

这 5 组场景并不是完全独立的，它们之间有明显关系：

- 价格监控依赖价格类标准化
- 投资信息跟踪依赖价格类、新闻 / 公告类、金融指标 / 事件类
- 内容更新跟踪依赖内容更新类
- 趋势 / 热度跟踪目前还不进入第一版主流程

## 4. 第一阶段主场景

### 4.1 主场景 A：价格监控

这是第一阶段优先级最高的场景。

#### 用户目标

- 不再手动反复查看多个平台
- 第一时间发现值得关注的低价
- 能回看一段时间内的价格变化

#### 当前典型样本

- `Surface Pro 8 16G + 512G` 二手价格
- 某只股票价格变动
- 黄金价格变动
- 每日宽基指数收盘结果

#### 第一阶段要解决的核心任务

1. 围绕某个主题接入多个价格来源
2. 把同主题的跨平台同配置价格标准化存下来
3. 支持历史价格回看
4. 识别最近 30 天新低
5. 对高价值价格变化进行提醒

#### 为什么优先级最高

- 角色优先级最高的消费者需求直接对应这个场景
- 真实样本最明确
- 价值判断最直接
- 抓取、标准化、历史和提醒链路都能被完整锻炼

### 4.2 主场景 B：投资信息跟踪

这是第一阶段第二优先级场景。

#### 用户目标

- 不错过和自己关心标的或宏观主题有关的重要信息
- 能快速知道数据发布、政策变化、价格变化和相关公告
- 能看到信息的历史记录和基本方向性判断

#### 当前典型样本

- 统计局季度 GDP、CPI、人口统计数据
- 人民银行利率变化、资金投放与回收、新政策发布
- 每日宽基指数收盘结果
- 某只股票价格变动
- 黄金价格变动

#### 第一阶段要解决的核心任务

1. 围绕某个投资主题接入多个来源
2. 按金融指标 / 事件类和价格类标准化存储
3. 跟踪时间点数据与事件发布
4. 识别利空 / 利好事件
5. 对高价值金融事件进行提醒

#### 为什么排在第二位

- 它是已确认的第二优先角色核心需求
- 它能推动金融指标 / 事件类标准化落地
- 它能帮助验证“事实记录 + 初步方向判断”这套模式

## 5. 第一阶段支撑场景

### 5.1 支撑场景 A：新闻 / 公告跟踪

这个场景本身不是第一阶段主交付目标，但它是投资信息跟踪的重要支撑能力。

#### 用户目标

- 持续接收正式发布的信息
- 知道哪些新闻或公告与当前主题有关
- 为后续利空 / 利好判断保留证据基础

#### 当前典型样本

- 统计局公告
- 人民银行政策发布
- 公司公告
- 正式新闻源发布

#### 第一阶段定位

- 作为投资信息跟踪的事实来源层进入
- 先解决“能收集、能归档、能关联”
- 不要求一开始就做复杂新闻分析

### 5.2 支撑场景 B：内容更新跟踪

这个场景在第一阶段更多承担“能力预埋”的角色。

#### 用户目标

- 持续关注某个产品最近是否有新功能或新活动
- 为后续独立开发者场景和竞品动态场景打基础

#### 当前典型样本

- `Figma` 最近上线什么新功能
- 某个产品发布新的营销活动

#### 第一阶段定位

- 先进入标准化体系
- 先支持“有无更新”和“基础回看”
- 不作为第一阶段主打能力

#### 为什么暂不升为主场景

- 当前角色优先级中，独立开发者排在第三位
- 内容更新类对当前最紧迫的自用需求不是第一刚需
- 但它对后续扩展价值很高，因此不应完全延后

## 6. 暂缓场景

### 6.1 暂缓场景 A：趋势 / 热度跟踪

当前样本：

- 某 UGC 平台上有一个新的主题热度快速上升

#### 为什么先暂缓

- 它和当前第一阶段主场景不完全同构
- 对热度、趋势、异常的定义会明显拉高标准化复杂度
- 它更容易把产品从“信息工作台”拉向“舆情或趋势平台”

#### 当前策略

- 保留样本
- 进入后续观察池
- 等到具体实现阶段再决定是否纳入下一阶段

### 6.2 暂缓场景 B：复杂舆情和情绪分析

当前不进入第一阶段范围。

原因：

- 不属于当前主角色优先级中的前两项刚需
- 标准化和分析复杂度较高
- 容易分散当前抓取和沉淀主线

## 7. 场景与信息类型的对应关系

### 7.1 价格监控

主要依赖：

- 价格类

可选支撑：

- 新闻 / 公告类

### 7.2 投资信息跟踪

主要依赖：

- 金融指标 / 事件类
- 价格类

支撑依赖：

- 新闻 / 公告类

### 7.3 内容更新跟踪

主要依赖：

- 内容更新类

### 7.4 趋势 / 热度跟踪

目前未进入第一版主流程，暂不定义正式对应关系。

## 8. 阶段性优先级地图

### 8.1 Phase 1

主场景：

- 价格监控
- 投资信息跟踪

支撑场景：

- 新闻 / 公告跟踪
- 内容更新跟踪

暂缓场景：

- 趋势 / 热度跟踪
- 复杂舆情与情绪分析

### 8.2 Phase 2

预计增强：

- 价格监控的异常判断
- 投资信息跟踪的利空 / 利好事件筛选
- 内容更新跟踪的变化识别
- 同主题历史回看和研究能力

### 8.3 Phase 3

可能引入：

- 趋势 / 热度跟踪
- 更复杂的跨来源关联分析
- 更强的摘要与主题级洞察

## 9. 为什么这个优先级排序合理

### 9.1 和当前真实需求一致

你已经明确了当前最关心的是：

- 价格监控
- 投资信息跟踪

因此优先级必须围绕这两类场景组织。

### 9.2 和当前能力沉淀目标一致

你最想沉淀的是抓取能力。

而价格监控和投资信息跟踪正好最适合锻炼：

- 多来源接入
- 标准化存储
- 历史回看
- 异常识别

### 9.3 能避免前期产品范围膨胀

如果一开始把内容更新、UGC 热度、舆情分析全部拉进第一阶段，产品边界会明显变重。

当前排序能保留扩展可能，同时不破坏第一阶段收敛。

## 10. 当前版本的结论

当前已经可以明确：

- 第一阶段主场景是价格监控和投资信息跟踪
- 新闻 / 公告跟踪和内容更新跟踪是支撑场景
- 趋势 / 热度跟踪暂缓
- 第一版产品的设计和 MVP 范围，应优先围绕前两类主场景展开
